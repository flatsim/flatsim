## Overview - The Surface Level {#overview}

When migrating C++ code to Rust (or mixing both languages), you need a way for them to talk to each other. Think of it like translation:

- **CXX**: A two-way translator that speaks both languages fluently. Great for new code where you control both sides.
- **Bindgen**: A one-way translator that reads C++ and creates Rust equivalents. Great for using existing C++ libraries you can't change.

### Quick Analogy
Imagine you're building a house (Rust) next to an old mansion (C++):

- **CXX** = Building a fancy hallway connecting both buildings with proper doors, safety rails, and signs. You design it yourself.
- **Bindgen** = Discovering secret passages in the old mansion's walls and mapping them. You don't change the mansion.

## Why We Need FFI {#why-we-need-ffi}

Flatsim depends on several C++ libraries:

| Library | Purpose | Problem |
|---------|---------|---------|
| **Muli** | Physics engine | Pure C++, can't rewrite physics from scratch |
| **Rerun** | Visualization | Has Rust SDK (easy!) |
| **TBB** | Threading | Can replace with Rayon (Rust) |
| **ZeroMQ** | Messaging | Has Rust bindings |
| **Boost** | JSON, utilities | Can replace with serde |

**The Challenge**: We can't migrate everything at once. We need:
1. New Rust code to call old C++ code
2. Old C++ code to call new Rust code
3. Both to work together seamlessly

**The Solution**: Use **CXX** for our own code and **bindgen** for external libraries.

## CXX - Rust ↔ C++ Bidirectional Bridge {#cxx}

### The Surface: What CXX Does

CXX lets you:
1. Call Rust functions from C++
2. Call C++ functions from Rust
3. Share types between both languages (with safety guarantees)

### Simple Example from Flatsim

```rust
// rust/flatsim-ffi/src/lib.rs
#[cxx::bridge]
mod ffi {
    extern "Rust" {
        // Exposing Rust to C++
        fn rust_hello() -> String;
        fn vec2_example(x: f64, y: f64) -> f64;
    }
}

// Implementation
fn rust_hello() -> String {
    "Hello from Rust!".to_string()
}

fn vec2_example(x: f64, y: f64) -> f64 {
    let v = Vec2::new(x, y);
    v.length()  // Returns sqrt(x² + y²)
}
```

**C++ Side:**
```cpp
// Automatically generated by CXX
#include "rust/cxx.h"
#include "flatsim-ffi/src/lib.rs.h"

int main() {
    rust::String msg = rust_hello();
    double len = vec2_example(3.0, 4.0);  // Returns 5.0
    std::cout << msg << " Length: " << len << std::endl;
}
```

### What Just Happened?

1. **You wrote Rust code** with `#[cxx::bridge]`
2. **CXX generated C++ headers** automatically during build
3. **Both sides can talk** type-safely

## Bindgen - C++ → Rust Bindings {#bindgen}

### The Surface: What Bindgen Does

Bindgen reads C++ header files and automatically generates Rust code that can call C++ functions. It's one-way: C++ → Rust only.

### When to Use Bindgen

- Calling external C++ libraries (like Muli physics)
- Libraries you don't control
- Complex C++ APIs with many functions

### Simple Example: Calling Muli Physics

**Muli C++ Header (simplified):**
```cpp
// muli/muli.h
namespace muli {
    class World {
    public:
        World();
        void step(float dt);
        void add_body(Body* body);
    };
    
    class Body {
    public:
        void set_position(float x, float y);
    };
}
```

**Bindgen Build Script:**
```rust
// rust/flatsim-bind/build.rs
use std::env;
use std::path::PathBuf;

fn main() {
    println!("cargo:rerun-if-changed=wrapper.h");
    
    let bindings = bindgen::Builder::default()
        .header("wrapper.h")  // Points to muli/muli.h
        .parse_callbacks(Box::new(bindgen::CargoCallbacks))
        .generate()
        .expect("Unable to generate bindings");

    let out_path = PathBuf::from(env::var("OUT_DIR").unwrap());
    bindings
        .write_to_file(out_path.join("bindings.rs"))
        .expect("Couldn't write bindings!");
}
```

**Generated Rust Code (automatic):**
```rust
// Generated by bindgen
pub mod muli {
    pub struct World {
        _unused: [u8; 0],
    }
    
    extern "C" {
        pub fn muli_World_new() -> *mut World;
        pub fn muli_World_step(this: *mut World, dt: f32);
    }
}
```

**Using It in Rust:**
```rust
// rust/flatsim-bind/src/lib.rs
include!(concat!(env!("OUT_DIR"), "/bindings.rs"));

pub struct PhysicsWorld {
    world: *mut muli::World,
}

impl PhysicsWorld {
    pub fn new() -> Self {
        unsafe {
            Self {
                world: muli::muli_World_new()
            }
        }
    }
    
    pub fn step(&mut self, dt: f32) {
        unsafe {
            muli::muli_World_step(self.world, dt);
        }
    }
}
```

## Deep Dive: How CXX Works {#cxx-deep-dive}

### The Magic Behind the Curtain

When you write:
```rust
#[cxx::bridge]
mod ffi {
    extern "Rust" {
        fn rust_hello() -> String;
    }
}
```

CXX does this:

#### Step 1: Parse the Bridge Macro
- CXX reads your bridge definition at compile time
- Validates types are FFI-safe
- Generates two things:
  1. C++ header file
  2. Rust FFI glue code

#### Step 2: Generate C++ Header
```cpp
// Generated: flatsim-ffi/src/lib.rs.h
#pragma once
#include "rust/cxx.h"

namespace rust {
    inline namespace cxxbridge1 {
        rust::String rust_hello() noexcept;
    }
}
```

#### Step 3: Generate Rust Glue Code
```rust
// Generated (simplified)
#[export_name = "cxxbridge1$rust_hello"]
pub extern "C" fn __rust_hello() -> *mut std::os::raw::c_void {
    let result = rust_hello();
    // Convert rust::String to C++ compatible format
    Box::into_raw(Box::new(result)) as *mut _
}
```

#### Step 4: Type Safety Layer

CXX ensures:
- **Memory safety**: Ownership tracked across boundary
- **ABI compatibility**: C-compatible layout
- **Error handling**: Panics become C++ exceptions

### Example: Passing Complex Types

```rust
#[cxx::bridge]
mod ffi {
    struct Vec2Data {
        x: f64,
        y: f64,
    }
    
    extern "Rust" {
        fn add_vectors(a: &Vec2Data, b: &Vec2Data) -> Vec2Data;
    }
}

fn add_vectors(a: &ffi::Vec2Data, b: &ffi::Vec2Data) -> ffi::Vec2Data {
    ffi::Vec2Data {
        x: a.x + b.x,
        y: a.y + b.y,
    }
}
```

**What CXX Does:**
1. Creates C++ struct with same layout
2. Ensures alignment matches
3. Generates conversion functions
4. Handles moves/copies correctly

## Deep Dive: How Bindgen Works {#bindgen-deep-dive}

### The Process

```
C++ Headers → Clang AST → Bindgen Analysis → Rust Code
```

#### Step 1: Clang Parsing

Bindgen uses libclang to parse C++ headers:
```cpp
// muli/world.h
class World {
    void step(float dt);
private:
    float time;
};
```

**Clang AST** (Abstract Syntax Tree):
```
Class: World
  - Method: step
    - Return: void
    - Param: dt (float)
  - Field: time (float, private)
```

#### Step 2: Bindgen Analysis

Bindgen walks the AST and makes decisions:
- **Public methods** → Generate extern "C" function
- **Private fields** → Make opaque (can't access from Rust)
- **Complex types** → May generate wrapper types
- **Templates** → Often requires manual help

#### Step 3: Code Generation

```rust
// Generated bindings
#[repr(C)]
pub struct World {
    _unused: [u8; 0],  // Opaque! Can't see inside
}

extern "C" {
    pub fn World_step(this: *mut World, dt: f32);
}
```

### Why Opaque Structs?

C++ classes often have:
- Virtual tables (vtables)
- Private data
- Complex memory layout

Rust can't safely access these, so bindgen makes them "opaque" - you can only use pointers to them.

### Dealing with Complexity

For complex C++ (templates, multiple inheritance), you often need a **wrapper header**:

```cpp
// wrapper.h - Simplified C API
extern "C" {
    void* muli_world_new();
    void muli_world_step(void* world, float dt);
    void muli_world_free(void* world);
}

// wrapper.cpp - Implementation
extern "C" void* muli_world_new() {
    return new muli::World();
}

extern "C" void muli_world_step(void* world, float dt) {
    static_cast<muli::World*>(world)->step(dt);
}
```

Now bindgen can easily handle this!

## Practical Examples from Flatsim {#practical-examples}

### Example 1: Exposing Rust Vec2 to C++ (CXX)

**Goal**: Let C++ code use Rust's Vec2 implementation

```rust
// flatsim-ffi/src/lib.rs
use flatsim_core::Vec2;

#[cxx::bridge]
mod ffi {
    extern "Rust" {
        fn vec2_new(x: f64, y: f64) -> (f64, f64);
        fn vec2_length(x: f64, y: f64) -> f64;
        fn vec2_add(ax: f64, ay: f64, bx: f64, by: f64) -> (f64, f64);
    }
}

fn vec2_new(x: f64, y: f64) -> (f64, f64) {
    (x, y)
}

fn vec2_length(x: f64, y: f64) -> f64 {
    Vec2::new(x, y).length()
}

fn vec2_add(ax: f64, ay: f64, bx: f64, by: f64) -> (f64, f64) {
    let result = Vec2::new(ax, ay) + Vec2::new(bx, by);
    (result.x, result.y)
}
```

**C++ Usage:**
```cpp
#include "flatsim-ffi/src/lib.rs.h"

auto [x, y] = vec2_new(3.0, 4.0);
double len = vec2_length(3.0, 4.0);  // 5.0
auto [rx, ry] = vec2_add(1.0, 2.0, 3.0, 4.0);  // (4.0, 6.0)
```

### Example 2: Using Muli Physics from Rust (Bindgen)

**Goal**: Call C++ Muli library from Rust

```rust
// flatsim-bind/build.rs
fn main() {
    println!("cargo:rustc-link-lib=muli");
    println!("cargo:rerun-if-changed=wrapper.h");
    
    let bindings = bindgen::Builder::default()
        .header("wrapper.h")
        .allowlist_function("muli.*")
        .allowlist_type("muli::World")
        .opaque_type("muli::World")  // Make it opaque
        .generate()
        .unwrap();
    
    // Write to OUT_DIR
    let out_path = std::path::PathBuf::from(
        std::env::var("OUT_DIR").unwrap()
    );
    bindings
        .write_to_file(out_path.join("muli_bindings.rs"))
        .unwrap();
}
```

```rust
// flatsim-bind/src/lib.rs
include!(concat!(env!("OUT_DIR"), "/muli_bindings.rs"));

pub struct PhysicsWorld {
    ptr: *mut muli_World,
}

impl PhysicsWorld {
    pub fn new() -> Self {
        unsafe {
            Self { ptr: muli_world_new() }
        }
    }
    
    pub fn step(&mut self, dt: f32) {
        unsafe {
            muli_world_step(self.ptr, dt);
        }
    }
}

impl Drop for PhysicsWorld {
    fn drop(&mut self) {
        unsafe {
            muli_world_free(self.ptr);
        }
    }
}
```

### Example 3: Hybrid Approach - Best of Both Worlds

Sometimes you use **both**:

```rust
// Use CXX for our API
#[cxx::bridge]
mod ffi {
    extern "Rust" {
        type Simulator;
        fn simulator_new() -> Box<Simulator>;
        fn simulator_step(sim: &mut Simulator, dt: f32);
    }
}

// Use bindgen for Muli internally
use crate::bindings::PhysicsWorld;

pub struct Simulator {
    physics: PhysicsWorld,  // From bindgen
    time: f64,
}

fn simulator_new() -> Box<Simulator> {
    Box::new(Simulator {
        physics: PhysicsWorld::new(),
        time: 0.0,
    })
}

fn simulator_step(sim: &mut Simulator, dt: f32) {
    sim.physics.step(dt);  // Call C++ Muli
    sim.time += dt as f64;
}
```

## When to Use What {#decision-tree}

```
┌─────────────────────────────────────┐
│ Do you control both C++ and Rust?  │
└───────────┬─────────────────────────┘
            │
    ┌───────┴───────┐
    │               │
   YES             NO
    │               │
    │               └──► Use BINDGEN
    │                   (External libraries)
    │
    ┌────────────────────────────────┐
    │ Need bidirectional calls?      │
    └────────┬───────────────────────┘
             │
     ┌───────┴───────┐
     │               │
    YES             NO
     │               │
     ├──► Use CXX   │
     │   (Best)     │
     │              │
     └──────────────┴──► Could use cbindgen
                         (Rust → C++ only)
```

### Decision Matrix for Flatsim

| Component | Strategy | Tool | Reason |
|-----------|----------|------|--------|
| Vec2, Utils | Expose to C++ | **CXX** | We write both sides |
| Muli Physics | Call from Rust | **Bindgen** | External C++ library |
| New algorithms | Rust only | None | Pure Rust, no FFI needed |
| Rerun viz | Use Rust SDK | None | Rerun has native Rust! |
| Boost.JSON | Replace | None | Use serde instead |

## Common Pitfalls and Solutions {#pitfalls}

### Pitfall 1: Trying to Pass Complex Types Through CXX

**Problem:**
```rust
// This won't work!
#[cxx::bridge]
mod ffi {
    extern "Rust" {
        fn process(data: HashMap<String, Vec<f64>>);  // ❌ Too complex!
    }
}
```

**Solution:** Simplify or serialize
```rust
#[cxx::bridge]
mod ffi {
    extern "Rust" {
        fn process_json(json: &str);  // ✅ Pass as JSON string
    }
}

fn process_json(json: &str) {
    let data: HashMap<String, Vec<f64>> = 
        serde_json::from_str(json).unwrap();
    // ... process ...
}
```

### Pitfall 2: Forgetting `unsafe` with Bindgen

**Problem:**
```rust
// Bindgen raw functions
let world = muli_world_new();  // ❌ Compiler error!
```

**Solution:** Wrap in safe abstraction
```rust
pub struct World {
    ptr: *mut muli_World,
}

impl World {
    pub fn new() -> Self {  // ✅ Safe API
        unsafe {
            Self { ptr: muli_world_new() }
        }
    }
}
```

### Pitfall 3: Memory Leaks with CXX Strings

**Problem:**
```rust
fn leak_memory() -> String {
    String::from("data")  // Who owns this after C++ calls it?
}
```

**Solution:** CXX handles this automatically! Just return String directly:
```rust
fn no_leak() -> String {
    String::from("data")  // ✅ CXX manages lifecycle
}
```

### Pitfall 4: Calling C++ That Throws Exceptions

**Problem:**
```cpp
void might_throw() {
    throw std::runtime_error("Oops!");
}
```

From Rust via bindgen: **Undefined behavior!** Rust doesn't handle C++ exceptions.

**Solution:** Catch in C++ wrapper
```cpp
// wrapper.cpp
extern "C" bool safe_might_throw(char* error_buf, size_t buf_len) {
    try {
        might_throw();
        return true;
    } catch (const std::exception& e) {
        strncpy(error_buf, e.what(), buf_len);
        return false;
    }
}
```

```rust
pub fn safe_call() -> Result<(), String> {
    let mut error_buf = vec![0u8; 256];
    unsafe {
        if safe_might_throw(error_buf.as_mut_ptr() as *mut i8, 256) {
            Ok(())
        } else {
            let msg = String::from_utf8_lossy(&error_buf);
            Err(msg.to_string())
        }
    }
}
```

### Pitfall 5: Build System Integration Issues

**Problem:** CXX-generated headers not found during build

**Solution:** Proper CMake setup
```cmake
# Link the Rust library
target_link_libraries(my_app PUBLIC flatsim_ffi)

# Include CXX bridge headers
target_include_directories(my_app PUBLIC 
    ${CMAKE_BINARY_DIR}/cargo/build/${Rust_CARGO_TARGET}/cxxbridge
)
```

## Summary

### Quick Reference

| Need | Use | Complexity | Safety |
|------|-----|------------|--------|
| Call Rust from C++ | CXX | Low | High |
| Call C++ from Rust (your code) | CXX | Low | High |
| Call C++ libs from Rust | Bindgen | Medium | Manual |
| Generate C headers from Rust | cbindgen | Low | High |

### For Flatsim Specifically

1. **flatsim-core**: Pure Rust (no FFI)
2. **flatsim-ffi**: CXX bridge (expose Rust to C++)
3. **flatsim-bind**: Bindgen (use Muli and other C++ libs)

### Golden Rules

1. **Keep FFI boundaries simple** - primitives and POD types work best
2. **Wrap unsafe bindgen code** in safe Rust APIs immediately
3. **Use CXX when possible** - it's safer and easier
4. **Serialize complex data** - JSON across boundary is easier than complex types
5. **Test both sides** - write tests in both C++ and Rust
